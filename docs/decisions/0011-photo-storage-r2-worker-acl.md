# チェックイン写真の保存・配信: R2 + Worker プロキシによる ACL

## 状況

チェックイン機能（訪問記録）に写真添付を追加する（デザインモック Phase 3b 相当。CLAUDE.md の当初 MVP スコープ外だが、全画面実装方針で対象化）。写真の**保存先と配信方式**、および**閲覧制御（ACL）**を決める必要がある。

要件と将来像:

- **現時点**: アプリに共有機能は無く、全データが本人専用。写真も**アップロード者本人のみ閲覧**が要件。
- **将来**: サービスに SNS 要素を追加する場合、他ユーザーへの画像共有（公開/フォロー限定など）があり得る。
- 保存・配信は ADR-0007 のとおり**単一 Worker（Hono）＋ D1 / R2 bindings 直結**の構成上に載る。認証は ADR-0010 の**不透明 session_id ＋ サーバサイドセッション**で確立済み。ADR-0010 のスコープ記述「保護対象機能は将来」を、本 ADR が写真リソースで**実体化**する。

当初は保存・配信に **Cloudflare Images** を使う想定だった。しかし Images のアクセス制御は「画像を `requireSignedURLs` にし、アプリが署名 URL の発行を絞る」間接方式であり、「本人のみ／公開／フォロー限定」が混在する SNS 型 ACL へ拡張しづらい、という懸念が挙がった。

## 決定

**写真は R2（非公開バケット）を保存の正とし、閲覧は Worker のプロキシエンドポイントで毎リクエスト ACL 判定する。画像最適化（変換・バリアント）は必要になってから後付けする。**

三層で責務を分離する:

1. **保存 = R2（非公開バケット）**
   - 全画像はまず R2 に置く。**公開配信 URL（imagedelivery.net 等）は持たせない**。
   - オブジェクトキーは推測不能（例: `checkins/<checkin_id>/<uuid>`）。ただし推測不能性はセキュリティの主線ではなく、ACL は必ず Worker で担保する。

2. **ACL = Worker プロキシ**
   - 配信は `/api/...(photo)/:id` のような **Hono ルート経由**。ADR-0010 のセッション検証を通し、リクエストごとに可否判定して R2 から `stream` 返却。
   - **現時点の判定は「所有者のみ」**（`photo.owner_user_id === session.user_id`）だけを実装。
   - SNS 化時は**判定ロジックの追加のみ**で拡張（`visibility=public` を許可 / フォロー関係を許可 等）。保存構造・配信経路は不変。

3. **最適化 = Cloudflare Image Transformations（後付け・トリガー式）**
   - Images "製品" のストレージは使わず、必要になった段階で R2 上の画像に対し変換/リサイズ/WebP 化をかける。
   - 導入トリガー（いずれか）: 公開フィード等で**多数ユーザーが同一画像を閲覧**する要件が確定 / 配信バイト量・Worker CPU がボトルネック化 / 元画像サイズ起因の表示遅延が顕在化。トリガー到達時に別 Issue（必要なら別 ADR）で判断する。

### データモデル（SNS 化を"追加"で済ませる布石）

- 写真行に **所有者参照（`owner_user_id`）** と **`visibility`（`private` / `public` 等）** を持たせる。
- 現時点は全行 `private` 固定運用。SNS 化＝**`visibility` の値運用＋ ACL 分岐の追加**で済み、スキーマ変更（破壊的マイグレーション）を伴わない。

### 公開画像の配信性能（将来の懸念への布石）

- 「公開画像でも毎回 Worker を叩く」懸念は、`visibility=public` の応答に**長い `Cache-Control` を付与しエッジキャッシュ**させることで実質解消（毎回はオリジン Worker に到達しない）。
- 私的画像はキャッシュさせない（`private, no-store` 相当）。

### スコープ（本 ADR で決めること / 決めないこと）

- **決める**: 保存先＝ R2、配信＝ Worker プロキシ、ACL＝セッションによる所有者判定、`visibility` 列の布石、最適化の後付け方針。
- **決めない（将来）**: SNS 共有の具体的モデル（公開範囲・フォロー・タイムライン）、画像変換パイプラインの具体、EXIF 除去やモデレーション等の運用。これらは要件化時に別途決定する。

## 理由

### R2 + Worker プロキシを選ぶ理由

1. **ACL 進化への強さ** — 判定が自前コードなので「本人のみ → 公開 → フォロー限定」のどの共有モデルにも**ポリシー追加だけ**で対応でき、SNS 化の要件変化を吸収できる。
2. **攻撃面が小さい** — 公開配信 URL が存在せず、閲覧は必ずセッション検証を通る。「本人のみ」を厳密に満たす。
3. **スタック整合** — R2 は ADR-0007 で Worker に binding 直結済み。追加のマネージドサービス（Images）を増やさず構成が単純。
4. **認証基盤の再利用** — ADR-0010 のセッション/user モデルをそのまま ACL に流用でき、実装・思考コストが低い。
5. **最適化は分離可能** — Image Transformations は R2 保存のまま後付けできるため、「今は過剰」な最適化を先送りしても将来塞がれない。

### 却下・保留した選択肢

- **A. Cloudflare Images（署名 URL 方式）**
  - ACL が「署名発行を絞る」間接方式で、**公開/限定/フォロー限定の混在モデルへ拡張しづらい**。
  - 署名 URL は有効期限付きで、一覧を長時間開く UX で**再発行**が要る。発行後は exp までは URL 漏洩で閲覧可能となり、厳密 ACL ではない。
  - Images の主戦場は「大量公開画像の最適配信」であり、現段階（本人専用・低volume）では過剰。ただし**将来 SNS で公開画像が主流化した場合の配信最適化**手段としては再検討余地があるため、完全な却下ではなく Image Transformations 併用の後付け候補として保留。
- **B. R2 を公開バケット化して直接配信**
  - URL 推測不能性頼みになり「本人のみ」を満たせない。却下。

### 既存 ADR との整合

- **ADR-0007（Workers 統合・R2 binding 直結）**: 本 ADR の配信は同一 Worker 内で R2 binding を直接叩く前提に乗る。矛盾なし。
- **ADR-0010（認証: session_id ＋ Origin 検証）**: ACL は 0010 のセッション検証を再利用。0010 の「保護対象機能は将来」を写真リソースで実体化する。アップロード等の状態変更系は 0010 の Origin/Referer 検証ミドルウェア配下に置く。
- **ADR-0004（OSM: 採用＋移行トリガー明文化パターン）**: 「今は R2 プロキシ、要件到達で Image Transformations を別途判断」という同型の運用を踏襲。
